# vpush Python 到 Rust 完整功能切换设计

日期：2026-09-27
状态：已获用户确认，待实施计划

## 目标

将 Python 生产版 vpush `1.12.277` 替换为 Rust 版，达到完整功能等价后再切换生产流量。最终 Rust 实例应成为唯一 Web 应用实现；Python 在切换前继续作为唯一线上服务和回滚目标。

允许最终 SQLite 同步时有短暂写入冻结。不采用双写或长期 Python/Rust 双轨代理。

## 不变约束

- 不修改任何主机的 `~/.ssh/authorized_keys`、`sshd_config`、sshd 服务、iptables/nftables/ufw 或 OCI 安全列表。
- 未经单独确认，不写入或覆盖 DMIT 生产 `/opt/vpush` 的数据库、`.env`、compose、Caddyfile 或容器。
- 不在生产使用 `docker compose run` 启动第二个 SQLite 进程，不执行生产 `docker compose build`。
- ARM 上的 xincai、xincai-push、IMA pull、OpenList、1Panel、NFS 和 SSH 隧道保持不变。
- 私钥、token、密码不写入仓库、日志、issue、commit 或聊天记录。
- 任何生产写操作、DNS/Caddy/网络修改和正式流量切换，先列出命令与影响，得到明确确认后再执行。

## 现状基线

- Python 生产后端：`1.12.277`，DMIT `179.255.150.134`，生产数据库 `/opt/vpush/data/dav.db`。
- Rust staging：Oracle ARM `167.234.213.74`，端口 8000，后端已对齐到 `1.12.277`，数据库独立。
- 生产数据库在线副本迁移演练已通过：`quick_check=ok`，核心记录数量保持一致，Rust schema 迁移成功。
- Rust 本地质量门禁已通过：113 个测试、Clippy、格式检查和 diff 检查。
- ARM 上发现 `xincai` 因“初始化安全密钥失败：Permission denied”重启；`xincai-push` 因未启用退出。不得把该问题静默归因于 vpush，需单独调查或明确边界。

## 分阶段设计

### 1. 基线与差异清单

从生产 Python `api.py` 和 Rust `main.rs` 提取：

- 路由、HTTP 方法、路径参数和认证要求。
- 请求体字段、响应 JSON 结构、错误状态码。
- 数据库读写表、迁移行为和副作用。
- 外部服务依赖、定时任务、推送和采集开关。

路由差异按以下组分类：

- 用户核心：登录、资料、密码、WebPush、Android device、订阅、Feed、文章、新闻、KOL。
- 管理功能：用户、注册码、KOL、分类、标签、推送日志、Turnstile、图床、代理、备份。
- 外部集成：飞书个人、飞书文档 OAuth、IMA、CICC、雪球、微博、Telegram、微信、LLM。
- 运维接口：健康、版本、日志、存储、恢复和同步。

每个缺口必须标记为“已补齐”“明确不适用”或“阻塞切换”，不能留下未解释缺口。

### 2. Rust 功能补齐

按用户影响和依赖顺序实施：

1. 登录、用户资料、WebPush、设备和订阅。
2. 文章、Feed、新闻和 KOL 用户流程。
3. 管理用户、注册码、KOL、分类、标签、推送日志。
4. 新闻管理、Turnstile、图床、代理、备份和恢复。
5. 飞书文档/个人、IMA 管理、CICC、OAuth 和采集控制。

优先复用现有 `main.rs`、`db.rs` 和已有模块。每组功能增加最小行为测试，敏感写操作使用隔离数据库和测试配置验证。

### 3. 配置映射

建立只包含变量名、来源、Rust 使用位置、是否必需、默认值策略和验证状态的映射表。禁止记录变量值。

生产变量分为：

- Rust 已读取且可直接映射。
- Rust 已读取但生产没有，需要补默认值或明确部署来源。
- 生产存在但 Rust 未读取，需要确认功能是否已补齐。
- 仅 Python/宿主机运行时使用，不应复制到 Rust。

生产 `.env` 不直接复制。Rust 的 `WEB_TOKEN_SECRET`、外部 API 密钥、VAPID 密钥和服务 token 只在目标主机本地配置，并通过脱敏状态检查验证。

### 4. 数据迁移与 staging 验收

- 用 SQLite 在线 backup 生成生产一致性副本，不停止生产服务。
- 原始副本只读保留，Rust 对独立工作副本执行 schema 迁移。
- 检查 `quick_check`、表清单、核心记录数量、关键索引和 WAL 状态。
- staging 中关闭自动抓取和真实推送，使用测试配置验证：登录/权限、用户资料、订阅、文章/新闻、管理员接口、图片/附件、备份、外部集成边界。
- 每个核心流程记录 HTTP 状态、响应结构、数据库变化和是否产生外部副作用。
- 验收完成后删除演练容器和副本；不删除主 staging 数据或其他 ARM 服务。

### 5. 切换演练

在不改生产流量的前提下演练完整顺序：

1. 保存当前 Python 容器、镜像摘要、Caddy upstream 和数据库状态。
2. 预构建并验证 Rust 镜像。
3. 模拟写入冻结和最终 SQLite backup。
4. 将最终副本导入隔离 Rust 实例并执行迁移。
5. 运行健康、版本、登录、核心页面和管理检查。
6. 模拟 upstream 切换和失败回滚，不修改正式 Caddy/DNS。

演练必须产生可执行的命令顺序和失败判定，不把实际生产数据用于破坏性测试。

### 6. 正式切换与回滚

正式切换前单独提交变更清单，包含：

- 写入冻结范围和预计时长。
- 最终备份路径、校验值和恢复命令。
- Rust 镜像 digest、容器配置和健康检查。
- Caddy upstream 修改命令及影响。
- 域名、端口和 TLS 依赖。
- 验收 URL、管理员检查项和停止条件。
- 回滚到 Python upstream 的命令、数据库恢复边界和责任人。

只有用户明确批准后才执行生产写操作和正式流量切换。切换失败优先恢复 Python upstream；不删除生产数据库、不覆盖原始备份，保留失败日志供分析。

## 验收门槛

正式切换前必须全部满足：

- 路由和关键行为没有未解释缺口。
- 配置映射中没有未确认的必需变量。
- Rust 与前端版本一致并通过本地和 ARM release 构建。
- 数据库副本 `quick_check=ok`，核心数据一致，迁移可重复。
- staging 核心业务和管理流程通过。
- 外部集成的真实副作用已关闭或逐项验证。
- xincai 等外部依赖状态已解释，且 vpush 切换不会破坏其接口。
- 切换和回滚演练通过。
- 用户明确批准正式生产写入和流量切换。

未满足任何一项时，保持 Python 生产流量不变。
